# Ontological Descent Harness (ODH)

**A model-agnostic research harness for detecting hidden ontological commitments, proposing alternative primitives, and designing falsifiable comparisons.**

ODH is an experimental metareasoning project. Most AI agents search for solutions *inside* a supplied representation. ODH explicitly investigates whether the representation's assumed primitives, boundaries, and constraints should be changed.

The goal is **not** to favor any specific ontology, including Dromatopy. A candidate is only useful when it preserves required invariants, survives criticism, and produces an advantage that can be tested independently.

## Research hypothesis

An external reasoning architecture can increase an LLM's rate of discovering useful changes in problem representation **without changing its weights**. That hypothesis has not yet been established.

## Current capabilities (v0.1 research prototype)

- Baseline solution followed by structured extraction of primitives, assumptions, dependencies, invariants, and unknowns.
- Competing candidate ontologies generated by explicit operations: **derive a primitive**, **invert a dependency**, **change the unit of analysis**, **factor a concept**, and **replace an object with a process**.
- Adversarial criticism, explicit reduction obligations, discriminating-test proposals, and provisional rubric evaluation.
- Machine-readable JSON and human-readable Markdown runs with all intermediate artifacts.
- Local **Codex CLI** or **Claude Code CLI** integration using their existing login sessions; **no OpenAI or Anthropic API keys are required by ODH**.
- Standard-library Python core, mockable provider interface, and offline unit tests.

**What it does not yet do:** independently establish that a new ontology is novel, mathematically valid, or empirically superior. Its evaluator is an LLM-based *triage mechanism*, not scientific verification. Candidates are labeled unverified.

## Quick start

Requires Python 3.11+ and either a locally installed, authenticated Codex CLI or Claude Code CLI.

```bash
git clone https://github.com/gnosis33/ontological-descent-harness.git
cd ontological-descent-harness
python -m pip install -e ".[dev]"
python -m pytest

# Authenticate with one provider first, using its official CLI workflow.
# Then run:
odh run --provider codex --problem "Design a more adaptive AI-agent orchestration harness." --candidates 3
# or
odh run --provider claude --problem-file examples/agent_orchestration.txt --candidates 3
```

Outputs are written to `runs/<timestamp>/report.json` and `report.md` (ignored by Git). The report includes the baseline, ontology audit, candidates, critiques, provisional scores, and suggested tests.

Provider adapters run a CLI subprocess with the reasoning prompt on standard input, in an isolated temporary working directory. The Codex adapter defaults to a read-only sandbox. CLI versions vary; override the command via `ODH_CODEX_CMD` or `ODH_CLAUDE_CMD` if necessary. These are trusted local executable commands, not prompts.

For a deterministic smoke test that does not contact a model:

```bash
odh run --provider fixture --problem-file examples/agent_orchestration.txt --candidates 2
```

The fixture is deliberately synthetic: it only verifies plumbing.

## Pipeline

```text
Problem
  ├─ Baseline solver
  └─ Ontology auditor → primitives / assumptions / invariants
       ├─ Candidate A: derive a primitive → critic → provisional evaluator
       ├─ Candidate B: invert a dependency → critic → provisional evaluator
       └─ Candidate C: change unit of analysis → critic → provisional evaluator
                           ↓
                 Ranked hypotheses + tests
```

The initial system uses a fixed branching budget, not an unrestricted recursive search. Future versions can add adaptive branching and selection informed by independent evaluation.

## Evaluation philosophy

A deeper-sounding ontology is **not automatically better**. A candidate must supply:
1. A clear account of which primitives are replaced or derived.
2. A reconstruction of the baseline's successful behavior.
3. A case that distinguishes it from a simpler extension of the baseline.
4. A concrete, reproducible test and a criterion for failure.
5. Measurable performance, expressivity, prediction, or simplicity improvement.

The engine scores only the quality of the *proposal* using model judgments. It cannot claim real-world validation. See [docs/research_protocol.md](docs/research_protocol.md) for the benchmark design.

## Safety and privacy

No model API keys are stored or required by ODH. Local coding assistants may have their own authentication and usage terms. Runs are saved locally. Do not include secrets or sensitive proprietary data in prompts. Code generated by a model is treated as untrusted text and **never automatically executed** by the harness.

## Status and roadmap

This is an early research implementation, **not** proof that ontological creativity has been improved. Next milestones: independent outcome-based evaluators, fixed benchmark cases with blinded scoring, multi-model replication, search-tree persistence, and ablations of each ontology operator.

Contributions, critical counterexamples, and negative results are welcome. See [CONTRIBUTING.md](CONTRIBUTING.md).
